# Internationalization (i18n)

The UI ships in **English** and **Russian**. The language can be changed at
runtime — no restart, no separate build — from the sign-in screen or the user
area. The choice is stored in `localStorage` under `discord-client.lang` and is
also reported to the backend so the few user-facing backend errors follow the
selected language.

## Files

| File | Purpose |
| --- | --- |
| `src/locales/en.json` | English dictionary (flat keys) |
| `src/locales/ru.json` | Russian dictionary |
| `src/i18n.ts` | detection, `t()`, DOM translation, persistence, events |
| `scripts/check-i18n.mjs` | key/placeholder parity check (`npm run i18n:check`) |
| `src-tauri/src/i18n.rs` | backend language flag + localized error strings |

Dictionaries are flat JSON objects. Keys use dot-separated namespaces:

```json
{
  "login.subtitle": "A lightweight client for calls and chat",
  "chat.empty": "No messages yet",
  "voice.error": "Error: {error}"
}
```

Placeholders use `{name}` and are interpolated by `t()`:

```ts
import { t } from './i18n';

status.textContent = t('status.reconnectingWithError', { error: detail });
```

## Runtime behaviour

1. `initI18n()` runs at the top of `src/app.ts`, before any UI rendering.
2. The language is chosen in this order: stored value → system locale
   (`navigator.language`, `ru*` → Russian) → English.
3. `applyLanguage()` sets `<html lang>`, updates all `data-i18n*` nodes, syncs
   both language selects, persists the choice, calls the backend
   `set_language` command, and dispatches a `dc:languagechange` window event.
4. Dynamic widgets subscribe via `onLanguageChange()` in `app.ts` and re-render
   from state. No reload is required.

### Static markup

Use attributes instead of hardcoded text:

```html
<p data-i18n="login.subtitle">A lightweight client for calls and chat</p>
<input data-i18n-placeholder="login.tokenPlaceholder" placeholder="Token" />
<button data-i18n-title="voice.mic" title="Microphone">🎙</button>
<li data-i18n-html="login.helpStep1">Open <b>discord.com</b> …</li>
```

Supported attributes:

- `data-i18n` → `textContent`
- `data-i18n-html` → `innerHTML` (only for trusted static strings)
- `data-i18n-placeholder` → `placeholder`
- `data-i18n-title` → `title`
- `data-i18n-aria-label` → `aria-label`

The text inside the element is the English fallback shown before JavaScript
runs. Keep it in sync with `en.json` when practical.

### Dynamic strings

Every user-facing string in TypeScript must go through `t()`. Do not concatenate
translated fragments; pass variables instead:

```ts
// Good
showError(t('members.loadError', { error: String(e) }));

// Bad: word order differs between languages
showError(t('members.loadErrorPrefix') + e);
```

If a widget stores a rendered message, store the **key and variables**, not the
translated text, so a language switch can re-render it. See `ui/voice.ts`,
`ui/status.ts` and `ui/stream.ts` for the pattern.

## Adding a string

1. Add the key to `src/locales/en.json`.
2. Add the same key to `src/locales/ru.json`.
3. Use it via `data-i18n*` (markup) or `t()` (TypeScript).
4. Run `npm run i18n:check` and `npm run fe:check`.

CI fails if a key is missing in either locale or if the `{placeholders}` differ.

## Adding a language

1. Copy `src/locales/en.json` to `src/locales/<code>.json` and translate values.
2. Register it in `src/i18n.ts`:

   ```ts
   import de from './locales/de.json';
   const DICTS: Record<Language, Record<string, string>> = { en, ru, de };
   export type Language = 'en' | 'ru' | 'de';
   ```

3. Extend `isLanguage()` accordingly.
4. Add an `<option value="de">DE</option>` to both `data-language-select`
   elements in `src/index.html`.
5. Add the locale to `scripts/check-i18n.mjs` (`const locales = [...]`).
6. Update the language detection if the new language should be auto-selected
   (e.g. `navigator.language.startsWith('de')`).
7. Run `npm run check` and test the switch in both the login screen and the app.

Please keep the filename/ISO code aligned (`de`, `fr`, `pl`, …) and use the
language's own name in the selector when it helps users (e.g. `DE`).

## Backend strings

Most backend errors are raw Discord/API details and stay in English. The handful
of strings that the backend returns directly are localized in
`src-tauri/src/i18n.rs`:

- the language is set by the `set_language` Tauri command;
- `crate::i18n::t(Key::…)` returns the string in the active language;
- unknown language tags fall back to English.

When you add a user-facing backend error, add a `Key` variant and both
translations. Do not add UI copy to the backend if the frontend could render it;
prefer returning structured data or a short error code.

## Conventions

- English is the source language and the fallback (`DICTS.en`).
- Keep keys stable; renaming a key requires updating all usages.
- Use sentence case, no trailing spaces, and the same punctuation as English.
- Russian uses `ё` where appropriate and follows the existing informal tone
  ("ты"), matching the rest of the UI.
- Do not translate brand names (`Discord`, `DAVE`, `Opus`, `OpenH264`).
- Emoji are part of the translation values; keep them consistent unless the
  language/culture requires a change.

## Code comments

Comments in the Rust and TypeScript sources are mostly **Russian**, a remnant of
the project's origin. They are not user-facing. Translating them to English is a
useful contribution and can be done file by file; see
[../CONTRIBUTING.md](../CONTRIBUTING.md). Do not mix a comment translation with
behavioural changes in the same PR.
